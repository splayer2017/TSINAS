## 1. Bloqueadores Estructurales

### [BLOCK-01] Desconexión Arquitectónica Total entre Gateway/Library y Swarm P2P (iroh-docs/gossip)
- **Severidad:** BLOQUEADOR ESTRUCTURAL (L3 / T3 / R1 / C3 = 10)
- **Categoría:** Streaming P2P / Modelo de Datos
- **Ubicación:** `Archivo: crates/core/src/library.rs` | `Líneas: 81-121, 159-196` y `Archivo: crates/cli/src/main.rs` | `Líneas: 183-193`
- **Evidencia:**
```rust
// crates/core/src/library.rs:101-114
let tag = self.store.blobs().add_path(&abs).await?;
let hash_s = tag.hash.to_string();
let tag_s = String::from_utf8_lossy(tag.name.as_ref()).to_string();
let mime = p2p_nube_vault_mime(&name);

self.db.upsert_file(&FileRow {
    path: path.clone(),
    hash: hash_s.clone(),
    size,
    mime: mime.clone(),
    policy: Policy::StreamOnly,
    host_id: self.endpoint_id.clone(),
    tag: tag_s,
})?;
```
- **Por qué bloquea la escalabilidad o rendimiento:** La arquitectura documentada en `README.md` establece: *"Fuente de verdad = iroh-docs; SQLite es solo proyección"*. Sin embargo, la estructura `Library` únicamente posee referencias a `BlobsStore` y a SQLite `Db`, careciendo por completo de referencia a `Docs` o `Gossip`. Cuando un usuario añade archivos, escanea carpetas o sube ficheros desde la interfaz web, el archivo **solo** se almacena en el `blobs_store` local y en SQLite. Jamás se publica en `iroh-docs` ni se emite por gossip. Si el servidor se arranca sin archivo inicial (caso documentado como estándar: `"arranca con la biblioteca vacía y todo se añade después desde la web"`), nunca se genera ningún `Doc` ni ningún ticket P2P. Los demás peers del swarm son incapaces de enterarse de la existencia de dichos archivos por vía P2P.
- **Solución más pequeña e idiomática en Rust:**
  1. Inyectar `docs: Docs` y `gossip: Gossip` en `Library::new(store, docs, gossip, db, endpoint_id)`.
  2. Persistir el `DocId` de la biblioteca activa en SQLite o configuración local para no recrear un doc vacío en cada arranque.
  3. Al invocar `add_file`/`add_upload`, publicar la entrada en `Doc::set_hash` (o serializar `SharedFile` en el doc) además de indexar en SQLite.
  4. Configurar un watcher asíncrono (`doc.subscribe()`) que proyecte automáticamente las mutaciones de `iroh-docs` hacia SQLite.
- **Costo de ignorarlo:** El sistema no funciona como red P2P distribuida; los archivos agregados dinámicamente son invisibles para cualquier nodo secundario o cliente móvil P2P nativo, reduciendo la aplicación a un simple servidor web HTTP centralizado.
- **Esfuerzo:** Medio

### [BLOCK-02] Política de Descarga por Defecto (`DownloadPolicy::Everything`) en `iroh-docs` Anula el Modo `StreamOnly`
- **Severidad:** BLOQUEADOR ESTRUCTURAL (L3 / T2 / R2 / C3 = 10)
- **Categoría:** Streaming P2P / Memoria y Zero-Copy
- **Ubicación:** `Archivo: crates/core/src/node.rs` | `Líneas: 53-56` y `Archivo: crates/core/tests/two_nodes.rs` | `Líneas: 57-64`
- **Evidencia:**
```rust
// crates/core/tests/two_nodes.rs:57-63
// El contenido también debe haberse sincronizado (DownloadPolicy por defecto = todo).
let bytes = b
    .blobs_store
    .blobs()
    .get_bytes(entry.content_hash())
    .await?;
assert_eq!(&bytes[..], &value[..]);
```
- **Por qué bloquea la escalabilidad o rendimiento:** El propósito fundamental de TSINAS es *"StreamOnly: Android reproduce sin descargar; sin persistencia a disco (solo RAM)"*. Sin embargo, en el motor `iroh-docs`, la política de descarga predeterminada al importar un ticket es descargar automáticamente el contenido completo de todos los blobs asociados (`DownloadPolicy::Everything`). En ningún lugar del código se configura `DownloadPolicy::Nothing`. Si un nodo receptor o peer móvil importa el ticket de una biblioteca con 50 GB de series en MKV, `iroh-docs` comenzará a saturar el ancho de banda y descargar los 50 GB al almacenamiento local (`data_dir/blobs/blobs.db`), colapsando la memoria o disco del dispositivo móvil.
- **Solución más pequeña e idiomática en Rust:**
  Al crear o importar un documento en nodos con política `StreamOnly`, configurar explícitamente la política de descarga en `iroh-docs`:
```rust
use iroh_docs::engine::DownloadPolicy;
doc.set_download_policy(DownloadPolicy::Nothing).await?;
```
- **Costo de ignorarlo:** Agotamiento catastrófico de almacenamiento (Disk Full / OOM) en clientes receptores y móviles, además de saturación del canal de subida del host.
- **Esfuerzo:** Bajo

### [BLOCK-03] Staging No Acotado de Subidas en `/tmp` (tmpfs) Sin Limpieza RAII
- **Severidad:** BLOQUEADOR ESTRUCTURAL (L3 / T2 / R2 / C3 = 10)
- **Categoría:** Memoria y Zero-Copy / Concurrencia Asíncrona
- **Ubicación:** `Archivo: crates/core/src/gateway.rs` | `Líneas: 270-353`
- **Evidencia:**
```rust
// crates/core/src/gateway.rs:270-271, 321-340
const MAX_UPLOAD: u64 = 8 * 1024 * 1024 * 1024;
let staging_dir = std::env::temp_dir().join("p2p-nube-uploads");
...
let mut out = match tokio::fs::File::create(&staged).await { ... };
...
loop {
    match field.chunk().await {
        Ok(Some(chunk)) => {
            written += chunk.len() as u64;
            ...
            out.write_all(&chunk).await ...
        }
        ...
    }
}
```
- **Por qué bloquea la escalabilidad o rendimiento:**
  1. En la inmensa mayoría de distribuciones Linux modernas, `/tmp` (`std::env::temp_dir()`) es un montaje `tmpfs` en memoria RAM. Permitir subir archivos de hasta 8 GiB a `/tmp` provocará que una sola subida o dos subidas concurrentes agoten de inmediato la memoria física del host, activando el Linux Kernel OOM Killer y matando el proceso del nodo.
  2. Ausencia de RAII: Si el cliente web/móvil aborta la subida o se desconecta a mitad de la transferencia (por ejemplo en el 50% de un archivo de 4 GB), Tokio cancela el future de `api_upload` en el punto de suspensión `.await`. Las líneas de borrado en caso de error (`tokio::fs::remove_file`) **nunca** se ejecutan, dejando archivos huérfanos de múltiples gigabytes en `/tmp` indefinidamente.
  3. Doble I/O: El archivo se escribe entero en `/tmp` y luego `store.blobs().add_path(staged)` lo lee entero para copiarlo/hashearlo al store persistente, duplicando la carga de I/O en disco.
- **Solución más pequeña e idiomática en Rust:**
  1. Utilizar un directorio de staging ubicado dentro de `data_dir/uploads` (en el mismo sistema de archivos persistente que `blobs/`, nunca en `std::env::temp_dir()`).
  2. Implementar un guardia RAII (o utilizar `tempfile::NamedTempFile` en un hilo bloqueante / wrapper asíncrono) cuyo `Drop` elimine el archivo si el handler no completa con éxito:
```rust
struct TempStagedFile(PathBuf);
impl Drop for TempStagedFile {
    fn drop(&mut self) {
        let _ = std::fs::remove_file(&self.0);
    }
}
```
- **Costo de ignorarlo:** Caídas del servidor por OOM provocadas por el kernel, corrupción de memoria de swap y agotamiento total del disco o RAM del sistema anfitrión.
- **Esfuerzo:** Medio

### [HIGH-01] Bug Funcional en Parsing de Rangos HTTP Suffix (`bytes=-N`) en Streaming de Video
- **Severidad:** DEUDA ALTA (L2 / T3 / R3 / C3 = 11)
- **Categoría:** Streaming P2P
- **Ubicación:** `Archivo: crates/core/src/gateway.rs` | `Líneas: 614-638`
- **Evidencia:**
```rust
// crates/core/src/gateway.rs:614-638
let start: u64 = if a.is_empty() {
    // suffix: últimos N bytes
    let suffix: u64 = b.parse().unwrap_or(0);
    if suffix == 0 {
        return Ok((0, total - 1));
    }
    total.saturating_sub(suffix)
} else {
    a.parse().map_err(...)?
};
let end: u64 = if b.is_empty() {
    total - 1
} else {
    b.parse().map_err(...)?
};
if start >= total || end >= total || start > end {
    return Err((StatusCode::RANGE_NOT_SATISFIABLE, ...).into_response());
}
```
- **Por qué bloquea la escalabilidad o rendimiento:** Cuando un cliente solicita un rango sufijo (por ejemplo `Range: bytes=-500` en un archivo de 10,000 bytes, habitual en reproductores multimedia como VLC o ExoPlayer para leer el atom `moov` al final de archivos MP4), `a` está vacío y `b` vale `"500"`. El código calcula correctamente `start = 9500`, pero en el cálculo de `end`, como `b.is_empty()` es falso, parsea `b` y asigna `end = 500`. Luego, la validación `start > end` (`9500 > 500`) se cumple y rechaza la petición con `416 RANGE_NOT_SATISFIABLE`.
- **Solución más pequeña e idiomática en Rust:**
```rust
let (start, end) = if a.is_empty() {
    let suffix: u64 = b.parse().map_err(|_| (StatusCode::RANGE_NOT_SATISFIABLE, "rango inválido").into_response())?;
    if suffix == 0 { (0, total - 1) } else { (total.saturating_sub(suffix), total - 1) }
} else {
    let start: u64 = a.parse().map_err(|_| (StatusCode::RANGE_NOT_SATISFIABLE, "rango inválido").into_response())?;
    let end: u64 = if b.is_empty() { total - 1 } else { b.parse().map_err(|_| (StatusCode::RANGE_NOT_SATISFIABLE, "rango inválido").into_response())? };
    (start, end)
};
```
- **Costo de ignorarlo:** Fallos inmediatos de reproducción (error 416) al intentar reproducir o saltar al final del video en clientes compatibles con HTTP Range.
- **Esfuerzo:** Bajo

### [HIGH-02] Bloqueo Síncrono de Hilos Tokio por Mutex de SQLite (`rusqlite::Connection`) en Pipeline de Streaming
- **Severidad:** DEUDA ALTA (L2 / T2 / R2 / C3 = 9)
- **Categoría:** Concurrencia Asíncrona / Rendimiento
- **Ubicación:** `Archivo: crates/core/src/db.rs` | `Líneas: 21-24, 117-123` y `Archivo: crates/core/src/gateway.rs` | `Líneas: 489-494, 520, 580`
- **Evidencia:**
```rust
// crates/core/src/gateway.rs:489-494
fn mime_for(state: &Gateway, hash_s: &str) -> String {
    match state.db.get_by_hash(hash_s) {
        Ok(Some(row)) if !row.mime.is_empty() => row.mime,
        _ => "application/octet-stream".to_string(),
    }
}

// crates/core/src/db.rs:117-123
pub fn get_by_hash(&self, hash: &str) -> anyhow::Result<Option<FileRow>> {
    let conn = self.inner.lock().unwrap();
    let mut stmt = conn.prepare("SELECT ... FROM files WHERE hash=?")?;
    ...
}
```
- **Por qué bloquea la escalabilidad o rendimiento:**
  1. Cada petición `GET /stream/:hash` y `HEAD /stream/:hash` ejecuta `mime_for`, la cual adquiere un `std::sync::Mutex` síncrono y ejecuta consultas I/O síncronas contra SQLite directamente sobre los hilos del runtime de Tokio.
  2. Durante la reproducción de video por streaming, un solo cliente emite decenas de peticiones Range consecutivas (trozos de 1–2 MB o seeks). Múltiples clientes concurrentes generan una contención brutal sobre el único `Mutex<Connection>`, paralizando los worker threads de Tokio.
  3. No se configura modo WAL (`PRAGMA journal_mode=WAL`), por lo que cualquier escritura concurrente (`upsert_file` durante escaneo o subidas) bloquea toda la base de datos a nivel de tabla con un lock exclusivo.
- **Solución más pequeña e idiomática en Rust:**
  1. Activar WAL mode en `ensure_schema`: `conn.execute_batch("PRAGMA journal_mode=WAL;")?;`.
  2. En el gateway, evitar consultar SQLite en cada paquete Range: cachear los tipos MIME en un `moka::future::Cache` o `DashMap<String, String>` en memoria, o consultar el MIME una sola vez o resolverlo por extensión del archivo sin tocar SQLite en el loop caliente.
  3. Reemplazar `Arc<Mutex<rusqlite::Connection>>` por `tokio_rusqlite` o despachar las operaciones de BD mediante `tokio::task::spawn_blocking`.
- **Costo de ignorarlo:** Caída en picado del rendimiento de streaming y latencias impredecibles de decodificación ante cargas concurrentes moderadas.
- **Esfuerzo:** Medio

### [HIGH-04] Tamaño de Buffer Subóptimo (4 KiB) en `ReaderStream` en Streaming de Alto Bitrate
- **Severidad:** DEUDA ALTA (L2 / T2 / R3 / C3 = 10)
- **Categoría:** Rendimiento y Streaming Zero-Copy
- **Ubicación:** `Archivo: crates/core/src/gateway.rs` | `Líneas: 572-574`
- **Evidencia:**
```rust
// crates/core/src/gateway.rs:572-574
let limited = reader.take(len);
let stream = ReaderStream::new(limited);
let body = Body::from_stream(stream);
```
- **Por qué bloquea la escalabilidad o rendimiento:** `tokio_util::io::ReaderStream::new` utiliza por defecto una capacidad de buffer interna de 4096 bytes (4 KiB). Al transmitir videos de alta definición (1080p a 10 Mbps o 4K a 40–80 Mbps), un stream de 4 KiB requiere entre 300 y 2,500 ciclos de sondeo asíncrono (`poll_read`), reallocation de chunks de bytes y llamadas a syscalls por segundo por cada cliente conectado.

```rust
let stream = ReaderStream::with_capacity(limited, 64 * 1024);
```
- **Costo de ignorarlo:** Uso excesivo de CPU en el host y saturación del scheduler de Tokio durante streams concurrentes o bitrates altos.
- **Esfuerzo:** Bajo

## 3. Deuda Moderada

### [MED-01] Inconsistencia en Borrado de Archivos con Mismo Hash (`remove_by_hash`) y Fuga de Tags al Sobrescribir
- **Severidad:** DEUDA MODERADA (L1 / T1 / R2 / C2 = 6)
- **Categoría:** Modelo de Datos
- **Ubicación:** `Archivo: crates/core/src/db.rs` | `Líneas: 86-104, 117-130` y `Archivo: crates/core/src/library.rs` | `Líneas: 201-212`
- **Evidencia:**
```rust
// crates/core/src/db.rs:29-37
CREATE TABLE IF NOT EXISTS files(
    path TEXT PRIMARY KEY,
    hash TEXT NOT NULL,
    ...
);
...
// crates/core/src/db.rs:127-129
pub fn delete_by_hash(&self, hash: &str) -> anyhow::Result<bool> {
    let conn = self.inner.lock().unwrap();
    let n = conn.execute("DELETE FROM files WHERE hash=?", [hash])?;
    Ok(n > 0)
}
```
- **Por qué bloquea la escalabilidad o rendimiento:**
  1. La clave primaria de la tabla `files` es `path`, pero el endpoint de eliminación es `DELETE /api/files/:hash`. Si un usuario tiene dos copias o enlaces simbólicos de un mismo video con diferente ruta (mismo hash Blake3), al eliminar uno se borran **ambos** de la base de datos sin previo aviso.
  2. En `upsert_file`, al actualizar una fila existente para una ruta con un nuevo hash/tag (`ON CONFLICT(path) DO UPDATE SET ...`), el tag anterior nunca se elimina de `store.tags()`. Dicho blob huérfano quedará protegido contra el Garbage Collector de iroh indefinidamente, provocando fuga de disco.
- **Solución más pequeña e idiomática en Rust:**
  1. Identificar registros por un ID único o por `path` en lugar de por `hash` para operaciones de borrado.
  2. Antes de reemplazar el tag en `upsert_file`, consultar si existía un tag previo y eliminarlo del tag store de iroh.
- **Costo de ignorarlo:** Fugas de espacio en disco en el store de blobs y borrado colateral accidental de archivos duplicados.
- **Esfuerzo:** Medio

```rust
// crates/core/src/tailnet.rs:6, 22-25
let out = Command::new("tailscale").args(["ip", "-4"]).output()?;
...
let out = Command::new("tailscale").args(["status", "--json"]).output().ok()?;
```
- **Por qué bloquea la escalabilidad o rendimiento:** `Command::new("tailscale")` invoca el ejecutable del sistema operativo de manera completamente síncrona. Si el daemon `tailscaled` está ocupado, resolviendo conexiones o bajo suspensión del sistema, el hilo que efectúa la llamada se bloqueará hasta que finalice el proceso o falle el socket IPC local.
- **Solución más pequeña e idiomática en Rust:**
  Utilizar `tokio::process::Command` para operaciones de red/CLI fuera de la fase de inicio síncrona.
- **Costo de ignorarlo:** Bloqueos temporales en llamadas a funciones de diagnóstico de tailnet.
- **Esfuerzo:** Bajo

## 5. Lo que está Bien (Fortalezas)
1. **Streaming Asíncrono Eficiente en Disco:** El uso de `tokio_util::io::ReaderStream` en combinación con `BlobReader::take` y `Body::from_stream` evita cargar archivos enteros en memoria RAM durante la reproducción de video.
2. **Integración Sólida con Blake3 Tree Hashing:** El empleo de `iroh-blobs` garantiza hashing criptográfico verificado por bloques (Bao / Blake3) con chunks de 1 KiB, permitiendo validación de integridad automática.
3. **Mecanismo de Des-pineo y Garbage Collection (GC):** Se incluye configuración explícita de `GcConfig` (ciclos cada 60s) y preservación de tags en el blob store. Al eliminar archivos desde la web, los tags correspondientes se borran para que el motor de blobs reclame el espacio en disco automáticamente.
4. **Diseño de Pruebas Unitarias Rápidas con Mocks en Memoria:** Las pruebas de `gateway` y `library` se ejecutan en 0.5 segundos gracias al desacoplamiento con `MemStore::new()` y `Db::open_in_memory()`, lo que permite validar peticiones de rangos HTTP 206 y lógica de escaneo sin requerir sockets de red reales ni tocar disco persistente.
5. **Algoritmo de Orden Natural:** La función `natural_key` en `library.rs` maneja de manera impecable el orden de capítulos de video (`cap2 < cap10`), resolviendo un problema típico en bibliotecas multimedia.
6. **Resolución Idempotente de Crypto Providers:** La invocación explícita de `rustls::crypto::ring::default_provider().install_default()` previene conflictos de compatibilidad entre `ring` (requerido por `iroh`) y `aws-lc-rs` (usado por `axum-server`).

## 6. Riesgos Futuros (Escalabilidad P2P)

### [FUT-01] Sobrecarga de Gossip y Tráfico QUIC sin Límite al Superar >500 Peers Concurrentes
- **Categoría:** Tamaño del Swarm / Ancho de Banda
- **Condición Gatillo:** Swarms con más de 100–500 peers concurrentes conectados a través de relays públicos de N0 o en la misma tailnet.
- **Impacto Proyectado:** La instancia actual de `iroh-gossip` carece de filtros de subscripción y límites de buffering en el router QUIC. Mensajes continuos de presencia o anuncios de catálogos generarán amplificación de tráfico y saturación de ancho de banda en nodos de baja potencia.
- **Mitigación Preventiva:** Implementar topics de gossip diferenciados con expiración de mensajes, amortiguación (debouncing) en la propagación de eventos de biblioteca y control estricto de peers activos.

### [FUT-02] Falta de Transcodificación Dinámica para Streaming 4K HEVC/AV1 hacia Clientes Móviles Web Heterogéneos
- **Categoría:** Streaming P2P / Ancho de Banda
- **Condición Gatillo:** Reproducción directa en navegadores móviles (Chrome/Firefox Android) de archivos con códecs MKV HEVC o pistas de audio FLAC sin transcodificar.
- **Impacto Proyectado:** Los navegadores no pueden reproducir de forma nativa estos contenedores y códecs, forzando al usuario a recurrir a reproductores externos (VLC).
- **Mitigación Preventiva:** Diseñar una capa de remuxing ligero al vuelo (remux a fMP4/HLS) o transcodificación asíncrona delegada en hardware (VA-API / NVENC) para clientes que no soporten el códec original.

### [FUT-03] Agotamiento de Memoria y Latencia en API `/api/files` con Bibliotecas de >10,000 Archivos (Falta de Paginación)
- **Categoría:** Rendimiento de Almacenamiento / Modelo de Datos
- **Condición Gatillo:** Bibliotecas locales o importadas que superen los 10,000 archivos de video.
- **Impacto Proyectado:** `db.list_files()` extrae todos los registros de una sola vez en un `Vec<FileRow>`, cargando megabytes de cadenas en memoria y bloqueando la interfaz web al serializar un JSON masivo.
- **Mitigación Preventiva:** Incorporar parámetros de paginación (`limit`, `offset` o cursor por nombre) en `db.list_files` y en el endpoint `GET /api/files`.
